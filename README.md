# OpenAI-совместимый LLM-шлюз

Проект запускает FastAPI-шлюз перед любым бэкендом, который предоставляет
OpenAI-совместимый API `/v1/*`. Шлюз намеренно не привязан к конкретному
бэкенду: vLLM и SGLang даны лишь как варианты развёртывания.

Шлюз:

- проксирует `/v1/chat/completions` с поддержкой потокового и непотокового режимов;
- проксирует все остальные маршруты `/v1/*` как обобщённые OpenAI-совместимые маршруты;
- пишет компактные события запросов/ответов/ошибок в Loki;
- отдаёт собственные Prometheus-метрики шлюза на `/gateway/metrics`;
- проксирует метрики бэкенда на `/metrics`;
- отправляет OpenTelemetry-трассы в OTLP-коллектор, когда это включено;
- отслеживает первый запрос в сессии по заголовку `X-Session-ID` с помощью Valkey;
- сохраняет в Valkey каждый обмен сессии: уникальные сообщения и объявления
  инструментов по хешу, а для каждого хода — что прислал клиент, что ответила
  модель, `usage`, `finish_reason`, обрывы и ошибки;
- дочитывает ответ бэкенда до конца, даже если клиент отключился на середине
  стрима, чтобы транскрипт содержал ход целиком.

Шлюз предоставляет два отдельных эндпоинта метрик: `/gateway/metrics` — для
собственных Prometheus-метрик шлюза, и `/metrics`, который проксирует эндпоинт
метрик бэкенда (возвращая `503`, когда бэкенд недоступен). Оба читает
`gateway-vmagent` из стека шлюза и отправляет в центральный VictoriaMetrics;
метрики узла и GPU так же отправляет `llm-vmagent` из стека LLM.

## Структура

```text
gateway/               код FastAPI-шлюза
deploy/build_images.sh сборка образов с фиксированной версией и запись тега в .env
deploy/llm             compose-файлы LLM-движка, скрипты запуска, экспортеры узла и GPU, агент метрик
deploy/gateway         compose-файл шлюза и его агента метрик
deploy/observability   compose-файл центрального стека: Valkey, Loki, Tempo, OTEL, VictoriaMetrics
observability/         JSON-экспорты дашбордов для импорта в существующий Grafana/workspace
docs/                  справочник по развёртыванию, метрикам и трассировке
```

Развёртывание разделено на три стека, потому что у них разная кратность:
`deploy/llm` и `deploy/gateway` поднимаются на **каждой** машине с движком (по
одному шлюзу на процесс движка), а `deploy/observability` — **один раз** на
весь парк.

За этим стоит конкретная задача. Когда перед шлюзами стоит балансер, ходы одной
сессии уходят на разные машины. Общий Valkey делает так, что все шлюзы
дописывают один и тот же транскрипт, и диалог остаётся целым; общие Loki и
Tempo собирают события и трассы всех движков в одном месте, разделяя их меткой
`engine` (`GATEWAY_ENGINE_ID`).

Стек шлюза при этом от стека наблюдаемости не зависит: шлюз стартует и
проксирует, даже когда центральная машина недоступна. Доставка в Loki и Tempo —
push, её отказ только считается в метриках; метрики отправляет отдельный
агент, от которого шлюз не зависит; вызовы Valkey закрывает
предохранитель, поэтому лежащий Valkey не добавляет к запросам таймаутов.
Подробности — в [Развёртывании](docs/DEPLOY.md).

## Рекомендуемое развёртывание

Сначала создайте настройки развёртывания:

```bash
cp deploy/observability/.env.example deploy/observability/.env
cp deploy/observability/configs/valkey.example.conf deploy/observability/configs/valkey.conf
# отредактируйте deploy/observability/.env: OBSERVABILITY_HOST должен быть
# адресом, доступным машинам с движками, *_VOLUME — существующими каталогами
# (см. OBSERVABILITY_RUN_AS); в valkey.conf замените requirepass

cp deploy/llm/.env.example deploy/llm/.env
cp deploy/llm/serve_vllm.example.sh deploy/llm/serve_vllm.sh
cp deploy/llm/serve_sglang.example.sh deploy/llm/serve_sglang.sh
# отредактируйте deploy/llm/.env и скрипт запуска выбранного бэкенда

cp deploy/gateway/.env.example deploy/gateway/.env
# отредактируйте deploy/gateway/.env: обязательно GATEWAY_ENGINE_ID,
# GATEWAY_HOST_ID (= LLM_HOST_ID) и адреса центральной машины; пароль Valkey —
# в GATEWAY_VALKEY_URL
```

Соберите образы — скрипт сам запишет их теги в оба `.env`:

```bash
deploy/build_images.sh
```

На машины, которые не собирают сами, образы переносятся архивом: `--save-dir`
сохраняет его, `docker load -i` загружает (см. [Развёртывание](docs/DEPLOY.md)).

Поднимите центральный стек — один раз, на выбранной машине:

```bash
cd deploy/observability
docker compose --env-file .env -f docker-compose.yaml up -d
```

Списка машин центральному стеку не нужно: логи, трассы и метрики приходят по
push и уже несут метки `engine` и `host`.

Дальше — на каждой машине с движком. Сначала запустите один из вариантов
бэкенда и проверьте его напрямую.

vLLM:

```bash
cd deploy/llm
docker compose --env-file .env -f docker-compose.vllm.yaml up -d
docker compose --env-file .env -f docker-compose.vllm.yaml --profile test run --rm llm-smoke-tests
```

SGLang:

```bash
cd deploy/llm
docker compose --env-file .env -f docker-compose.sglang.yaml up -d
docker compose --env-file .env -f docker-compose.sglang.yaml --profile test run --rm llm-smoke-tests
```

Только после того, как smoke-тест бэкенда прошёл, запускайте стек шлюза и
проверяйте тот же путь запроса уже через шлюз:

```bash
cd deploy/gateway
docker compose --env-file .env -f docker-compose.yaml up -d
docker compose --env-file .env -f docker-compose.yaml --profile test run --rm gateway-smoke-tests
```

Smoke-тесты разделены на два набора:

- `deploy/tests/smoke/test_backend_contract.py` — только OpenAI-совместимый
  контракт (`/v1`): непотоковый ответ, SSE-стрим, tool calling, отсутствие
  reasoning-трейса. Он корректен для любого эндпоинта, поэтому его гоняют оба
  стека — и бэкенд напрямую, и шлюз.
- `deploy/tests/smoke/test_gateway_sessions.py` — только шлюз: персистенция
  диалога в Valkey через `/gateway/session/{session_id}` и
  `/gateway/session_list`. У бэкенда этих маршрутов нет, поэтому набор
  запускается лишь в стеке шлюза.

Какой набор выполняется, задаёт `command` соответствующего сервиса в compose,
так что обе команды выше запускаются без дополнительных флагов.

Если для развёртывания требуется вызов инструментов (tool calling), задайте
`SMOKE_CHECK_TOOLS=true` в `deploy/llm/.env` и `deploy/gateway/.env`; тогда
раннер также отправит запрос с вызовом инструмента и завершится с ошибкой, если
выбранный бэкенд или путь через шлюз не может вернуть OpenAI-совместимые
`tool_calls`. Оставьте значение `false`, когда инструменты не входят в
ожидаемый рантайм-контракт. Подробности — в [Развёртывании](docs/DEPLOY.md).

## Контракт бэкенда

Бэкенд должен предоставлять OpenAI-совместимый HTTP API по префиксу `/v1`. Шлюз
не зависит от специфичных для бэкенда Python-API или внутренностей движка.

Обязательно для основного пути:

- `POST /v1/chat/completions`
- потоковые ответы в OpenAI-совместимом формате SSE при `stream=true`

Обобщённое проксирование поддерживает также маршруты вида:

- `GET /v1/models`
- `POST /v1/completions`
- `POST /v1/embeddings`
- любой другой маршрут `/v1/*`, поддерживаемый бэкендом

## Сессии

Когда запрос к `/v1/chat/completions` содержит `X-Session-ID`, шлюз сохраняет
в Valkey DB 1 всё, что прошло через него в рамках сессии, — ничего не сводя и
не достраивая. Сессия — это четыре ключа с общим hash-tag `{session_id}`:

| Ключ | Тип | Что хранит |
| --- | --- | --- |
| `…{id}:messages` | HASH | каждое уникальное сообщение один раз: хеш → JSON |
| `…{id}:tools` | HASH | каждое уникальное объявление инструментов: хеш → JSON |
| `…{id}:turns` | LIST | по записи на каждый обмен, в порядке завершения |
| `…{id}:meta` | HASH | `created_at`, `updated_at`, накопительные счётчики |

Хеш — первые 32 hex-символа sha256 от канонического JSON сообщения (ключи
отсортированы, поля со значением `null`, `[]` или `{}` отброшены). Поэтому
сообщение, которое клиент присылает в каждом запросе заново, хранится один
раз, а ответ модели и его эхо от клиента совпадают, даже если бэкенд добавил к
ответу пустые поля. Сообщения, отличающиеся хоть одним заполненным полем, —
разные сообщения: например, ответ с `reasoning_content` и его эхо без него.

Запись хода в `turns`:

- `input` — хеши истории, которую прислал клиент, в его порядке;
- `output` — хеш ответа модели (`null`, если обмен не удался);
  `extra_outputs` — остальные варианты при `n > 1`;
- `tools` — хеш объявления инструментов этого запроса или `null`;
- аудит: `request_id`, `started_at`/`finished_at`, модель, параметры
  генерации, `status_code`, `finish_reason`, `usage`, `ttft_sec`/`e2e_sec`,
  способ доставки (`complete`, `drained_after_disconnect`,
  `client_disconnected`, `truncated`) и ошибка, если была.

Клиент может присылать всю историю, урезанное окно, переписанный
system-промпт или историю без уже обработанных вызовов инструментов — шлюзу
это безразлично: он ничего не сопоставляет, а лишь пишет то, что увидел.
Вызов инструмента, который клиент потом выбросил из истории, остаётся в
`messages` как `output` своего хода. Запись хода — одна транзакция MULTI/EXEC
без чтения (HSET, RPUSH, HINCRBY, EXPIRE), поэтому параллельные запросы в одну
сессию не мешают друг другу, а стоимость записи не растёт с длиной сессии.

Неудачные обмены тоже попадают в запись: у такого хода нет `output`, но есть
`error` со статусом и выдержкой из тела ответа.

Если клиент отключился посреди стрима, шлюз продолжает читать бэкенд в
отдельной задаче и сохраняет ход целиком (`delivery:
drained_after_disconnect`). Поведение ограничено `GATEWAY_DRAIN_TIMEOUT_SEC` и
`GATEWAY_DRAIN_MAX_BYTES` — при превышении ход помечается `truncated` — и
полностью отключается через `GATEWAY_DRAIN_AFTER_DISCONNECT`. Такой ответ
клиент не получил; в записи он остаётся отдельным ходом со своей пометкой и в
чужую историю не подмешивается.

Чтобы `usage` попадал в запись и для потоковых ответов, шлюз сам добавляет
к запросу `stream_options.include_usage`. Клиенту, который об этом не просил,
usage-событие не отдаётся: исходящий поток пересобирается по SSE-событиям и
лишнее событие из него вырезается.

- `GET /gateway/session_list` возвращает по одной сводке на каждую сохранённую
  сессию: `created_at`, `updated_at`, `message_cnt` (уникальных сообщений),
  `tools_cnt` (уникальных объявлений), `turn_cnt`, а также `age_sec` (время
  жизни с первого запроса), `idle_sec` (с последнего запроса) и
  `expires_in_sec` (остаток TTL). Необязательные `from` и `to` (epoch-миллисекунды,
  как `${__from}`/`${__to}` в Grafana) оставляют только сессии, активные в этом
  периоде: созданные не позже `to` и обновлённые не раньше `from`. Неверное
  значение даёт 400. Решение принимается по одному `:meta`, счётчики читаются
  только для прошедших фильтр.
- `GET /gateway/session/{session_id}` возвращает сессию целиком:
  `{schema_version: 3, metadata, messages, tools, turns}`. `messages` и
  `tools` — словари «хеш → значение» в порядке первого упоминания, `turns`
  отсортированы по `started_at` (ответ, дочитанный после отключения клиента,
  записывается позже запроса, который его сменил). `metadata` содержит те же
  счётчики и длительности, что и список, и `totals` — запросы, неудачи,
  токены. Добавьте `?pretty=1`, чтобы дополнительно получить
  `messages_pretty`/`tools_pretty`/`turns_pretty` (строки с JSON и отступами)
  для отображения.

Запись хода делает задача, которая читает бэкенд, и завершается она сразу
после последнего байта клиенту. Читатель, запросивший сессию мгновенно, может
опередить эту запись — при автоматических проверках дождитесь нужного
`turn_cnt`.

Сессии, записанные шлюзом до schema 3, лежат одним JSON под ключом без
hash-tag. `GET /gateway/session/{id}` отдаёт их как есть, пока у них не
истечёт TTL; в `session_list` они не попадают. Если такая сессия продолжилась
после обновления шлюза, эндпоинт показывает только новую часть.

Для разбора одной сессии из терминала есть `misc/dump_session.py`: он ходит в
`GET /gateway/session/{id}` и печатает запись целиком в JSON либо
человекочитаемый диалог (`--transcript`): ходы по порядку, каждое сообщение —
один раз, там, где оно впервые появилось, с аудитом в заголовке хода.

Дашборд `gateway-session-viewer` (см. `docs/DASHBOARDS.md`) отображает эти
эндпоинты как просмотрщик полного диалога.

## Логи

Корзины (buckets) событий в Loki:

- `request_generation` — запросы к `/v1/chat/completions`;
- `request_non_generation` — прочие запросы `/v1/*`;
- `response_generation` — ответы `/v1/chat/completions`, содержащие ответ модели;
- `response_non_generation` — все остальные ответы бэкенда;
- `gateway_error` — сбои, произошедшие до того, как появился ответ бэкенда.

События запросов и ответов включают `request_id`, опциональный `session_id`,
`session_first_request`, `trace_id` и `span_id`.
События запросов генерации включают очищенный `request_json` без тел сообщений,
`tool_call_count` и `fallback_params`, когда некорректные значения сэмплирования
были заменены.
События ответов генерации сохраняют полезную нагрузку бэкенда, `assistant_text`,
тайминги, статус и поля размера.
Потоковые ответы генерации сохраняются как валидный JSON-объект, содержащий
упорядоченные SSE-события.
События непотоковых ответов включают очищенные JSON-нагрузки, когда бэкенд
возвращает JSON.
Чувствительные заголовки, такие как `Authorization`, cookie и API-ключи,
маскируются.

## Трассы

При `GATEWAY_OTEL_ENABLED=true` инструментация FastAPI создаёт HTTP-спаны для
не исключённых маршрутов. Путь chat completion дополнительно создаёт
доменные спаны:

- `llm.gateway.request` — полный запрос chat completion, обработанный шлюзом;
- `llm.backend.request` — вызов бэкенда;
- `llm.session.flow` — работа с сессией на стороне шлюза;
- `valkey.operation` — операции Valkey на уровне сессий;
- `llm.stream_response` — итерирование потокового ответа.

Tempo и OTEL Collector живут в `deploy/observability`. Трассы всех шлюзов
попадают в один Tempo и разделяются ресурсным атрибутом `service.instance.id`,
который шлюз берёт из `GATEWAY_ENGINE_ID`. Атрибуты спанов, семантика ошибок и
советы по поиску — в [Трассах](docs/TRACES.md).
